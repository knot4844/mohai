# 오늘모해 Three.js 적용 검토

2026년 10월 11일 · 공식 최신 문서와 현재 로컬 코드 기준

**적용 가능하다.** 현재 그래프가 별도 모듈로 나뉘어 있어, 데이터와 네이버 지도 화면을 유지하면서 Three.js로 그래프 표현을 바꿀 수 있다. **사용자가 요구한 임팩트와 몰입감을 위해 첫 시제품부터 원근·공간 깊이·카메라 이동이 있는 실제 3D 탐색을 권한다.** 그래프를 화면의 주요 경험으로 삼고, 정확한 지리는 기존 지도 화면에서 함께 확인하도록 한다.

이번 결과는 코드 구조와 공식 기능에 대한 적용성 검토다. 모해에 Three.js를 설치·통합하거나 실제 휴대폰 성능을 측정한 결과는 아니다. 검토 과정에서 서비스 코드와 배포를 변경하지 않았다.

WebGPU는 HTTPS 등 보안 컨텍스트 조건이 있고 브라우저·장치 지원을 확인해야 한다. ‘최신 브라우저’라는 표현만으로 모든 휴대폰에서 가능하다고 보장하지 않는다. 기능 감지와 초기화 실패 처리, 실제 기기 검증을 함께 둔다. [MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)

## 현재 코드에 들어갈 자리

현재 [photo-graph.js](/Users/dyl/mohai/public/photo-graph.js)는 Canvas 기반 ForceGraph에 HTML 사진 버튼을 겹친다. 장소 좌표는 fx/fy로 고정하고 화면상 군집 펼침만 별도 처리한다. 사진 선택·hover·키보드 focus는 기존 정보 패널 콜백을 호출한다.

[app.js](/Users/dyl/mohai/public/app.js)는 mountPhotoGraph를 mountOntology라는 이름으로 가져와 지도 대신 보일 때 마운트한다. 네이버 지도는 별도 컨테이너다. 따라서 Three.js 모듈에도 같은 입력과 focus/destroy 생명주기를 제공하면 기존 목록·상세 정보와 연결할 수 있다. 다만 생성자를 교체하는 것만으로 사진·카메라·터치가 자동 이전되지는 않는다.

| 현재 요소 | 적용 때 할 일 |
| --- | --- |
| 장소·행사 조회 결과 | 렌더러 입력으로 유지하고 object/place/event ID 전달 |
| geographicLayout | 화면 지리 좌표를 Three.js 장면 좌표로 변환하는 어댑터 추가 |
| 원형 사진 버튼 | 초기에는 HTML 버튼을 유지하고 3D 위치와 동기화하거나, 텍스처 노드와 접근성 버튼을 함께 구현 |
| Canvas 연결선·입자 | Three.js 선·메시·입자로 재작성 |
| 클러스터 펼치기 | 화면 투영 후 겹침 계산을 유지. 저장된 위경도를 수정하지 않음 |
| onPlace/onLeave/focus | 기존 상세 패널 동작과 연결 |
| destroy/숨김/모션 정지 | 렌더 루프·GPU 자원·이벤트·텍스처 수명을 관리 |
| 모바일 터치 | 한 손가락 페이지 스크롤과 그래프 조작의 경계를 별도 설계 |

현재 구조는 순수 JavaScript다. 이 검토에서 React 전환을 요구할 근거는 없다. 새로운 모듈은 버전을 고정해 로컬 자산 또는 번들로 배포하고, 필요할 때 지연 로드하는 것이 적절하다. Vercel 배포 구조 자체를 바꿀 필요는 없지만 현재 복사 중심 빌드에 새 자산 배포 경로를 연결해야 한다. 이는 현재 프로젝트 구조에서 도출한 적용 판단이다.

네이버 지도 자체를 3D로 바꾸는 작업은 범위가 다르다. 첫 적용은 현재처럼 지도/그래프 모드를 분리한다. 지도 위에 Three.js를 직접 겹치려면 지도 투영·카메라·이벤트 동기화와 공급자 지원 범위를 별도로 확인해야 한다.

## 모해에서 얻을 수 있는 변화

첫 화면의 목표는 주변의 선택지를 하나의 공간으로 느끼게 하는 것이다. 주 카메라는 PerspectiveCamera를 쓰고, 장소 사진은 앞뒤 깊이가 다른 실제 3D 물체에 표시한다. 보는 방향에 따라 원근·겹침·시차가 달라지고, 대상을 선택하면 카메라가 그 장소로 접근한다. 텍스트와 사진의 가독성을 위해 카메라를 향하는 사진 판과 입체 테두리를 활용할 수 있다.

| 장면 | 제안하는 경험 | 데이터 경계 |
| --- | --- | --- |
| 진입 | 내 위치를 중심으로 주변 장소들이 깊이를 두고 차례로 드러남 | 실제 주변 후보를 사용하고 가짜 현재 위치를 만들지 않음 |
| 둘러보기 | 회전·확대에 따라 사진들이 서로 다른 속도로 움직이며 공간감을 줌 | 장면 좌표와 원본 위경도 별도 보존 |
| 장소 선택 | 선택한 사진 쪽으로 카메라가 이동하고 주변 대상은 배경으로 정리 | 선택된 Object ID와 상세 패널 연결 |
| 선택 확장 | 해당 장소의 행사·회차 등 실제 관련 대상이 주변에 펼쳐짐 | 이미 확보된 사실 관계부터 표현 |
| 다음 행동 | ‘먹기·마시기·쉬기’로 이어질 선택지가 등장하는 후속 경험 | Action/Activity·추천 근거 구축 이후 연결. 초기 시제품에서 보여주면 명시적 데모 데이터 |
| 실제 위치 확인 | 같은 선택 대상을 네이버 지도에서 확인 | 공간 연출의 선을 도로 경로나 이동시간으로 해석하지 않음 |

몰입감은 깊이만으로 만들지 않는다. 사진의 크기 차이, 선택 방향으로 흐르는 빛, 카메라가 대상을 중심으로 재구성하는 움직임을 함께 설계한다. 모든 노드의 지속적인 흔들림이나 강한 발광은 피하고, 사용자가 선택할 때 변화가 집중되게 한다. 이는 연출 제안이며 현재 구현된 화면이 아니다.

자유 탐색을 위해 OrbitControls의 회전·확대·이동과 관성을 사용할 수 있다. 모해에는 상하 뒤집힘을 제한하고 ‘내 위치로 복귀’를 둔다. 기본 터치 설정은 한 손가락 회전이라 기존 페이지 스크롤과 충돌하므로, 모바일 기본 화면에서는 탭 기반 카메라 이동을 제공하고 별도 ‘공간 둘러보기’ 모드에서 드래그 회전을 활성화하는 구성이 적절하다. [OrbitControls 공식 문서](https://threejs.org/docs/pages/OrbitControls.html)

이 연출은 데이터의 표현이다. Three.js가 장소 데이터, 추천 이유, 영업시간, 실제 도로 경로를 만들어 주지는 않는다. 온톨로지의 Object/Place/Event/Occurrence를 유지하고, Node·Edge와 카메라 상태는 조회 결과를 표현하는 화면 모델로 둔다. 장면의 노드 높이를 실제 고도나 인기라고 오해하게 표시하지 않는다. 지리 화면과 의미 중심 탐색 화면의 배치 차이를 설명한다.

## 성능과 접근성 검증 계획

Three.js나 WebGPU를 썼다는 사실만으로 기존 Canvas보다 빨라진다고 단정하지 않는다. 현재처럼 처음 몇 개 장소만 표시하는 장면은 GPU backend 변경보다 사진 크기·렌더 횟수·DOM 갱신 방식의 영향이 클 수 있다. 비교 측정이 필요하다.

초기 제안은 그림자와 전체 화면 광원 후처리를 최소화하고, 사진 해상도와 DPR 상한을 두고, 보이지 않는 탭/영역에서는 그리기를 멈추는 것이다. 종료 시 geometry·material·texture·renderer 자원을 해제한다. Three.js의 renderer와 texture에는 dispose 기능이 제공된다. [Renderer 자원 해제](https://threejs.org/docs/pages/WebGLRenderer.html), [Texture 자원 해제](https://threejs.org/docs/pages/Texture.html)

HTML 버튼의 키보드 선택·초점·이름과 기존 상세 패널을 유지한다. 화면상의 GPU 픽셀만으로 현재 접근성을 대체하지 않는다. reduced-motion, 동작 일시정지, 지원 실패 시 기존 2D 전환도 포함한다.

| 검증 항목 | 제안 방법과 통과 기준 |
| --- | --- |
| 기능 | 사진 선택·정보창·군집 펼침·지도 전환·필터 변경이 동일 대상 ID를 유지 |
| 지리 의미 | 공개 출발점과 동서남북 사례 검증, 화면 펼침이 원본 좌표를 바꾸지 않음 |
| 모바일 | 실제 iPhone Safari와 Android Chrome에서 스크롤·핀치·선택 검증 |
| 부하 | 동일한 24·100·300노드 시나리오로 기존2D, WebGL2, 가능한 WebGPU 비교 |
| 체감 | 조작 중 30fps 이상을 초기 목표로 하되 대상 기기·p95 frame time 기록. 달성한 수치가 아님 |
| 초기 비용 | 다운로드량·첫 그래프 표시 시간·긴 작업·이미지 로딩을 기존 화면과 비교 |
| 수명 | 지도/그래프 반복 전환 후 GPU 자원·메모리 누적 확인, 탭 숨김 시 루프 정지 |
| 실패 | WebGPU/WebGL2 초기화 실패·컨텍스트 손실·사진 로딩 실패 시 사용 가능한 대체 화면 |
| 사용성 | 선택 시간과 오조작이 기존보다 악화되면 효과 축소 또는 도입 보류 |

## 권고하는 다음 작업

먼저 독립된 시제품 화면에 실제 좌표가 있는 대표 데이터와 허가된 기존 사진을 연결한다. 실데이터 부족은 그래픽 대체로 표시하고, 현재 방문 가능성 테스트와 렌더링 테스트를 구분한다. 그 화면에서 **Three.js 직접 3D와 기존2D**를 비교하며 WebGPU는 지원되는 환경에서 추가 비교한다.

시제품의 핵심 완료 조건은 사진이 공간 안에 배치되고, 회전에 따른 시차와 선택 시 카메라 접근·복귀를 직접 체험할 수 있는 것이다. 다음 행동 추천 엔진은 기존 데이터 설계 순서에 따라 별도 진행한다.

현재 보고 단계의 판정은 ‘구조상 적용 가능, 구현 경로 명확, 운영 채택은 시제품 실측 후’다. Three.js 적용을 위해 사용자가 새 API ID나 서버 GPU를 준비할 필요는 없다. 실제 경로·새 장소·이미지 데이터 공급 권한은 렌더러와 별개의 문제다.
